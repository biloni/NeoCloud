# NeoCloud People OS — Project Brief

This file is the source of truth for this project. Read it fully before any task. When a requirement here conflicts with a general best practice, this file wins.

## What we are building

A deployed web app for a People Systems Lead take-home exercise. It simulates a lightweight People operations and workforce planning tool for NeoCloud Inc., a fictional ~350-person GPU cloud company (US, Canada, UK, India) preparing for IPO. The app demonstrates Workday-style thinking: effective-dated data, worker vs. position constructs, supervisory orgs, and a Business Process (BP) framework with multi-step approvals and audit trail.

## Grading rubric (build priorities in this order)

1. Data Model & Architecture — 25% (effective-dating, master vs. transactional separation, Workday concept mapping)
2. Business Process & Workflow — 20% (multi-step approval with conditional routing + audit trail; driver-based workforce planning scenarios)
3. Payroll Preview & GL — 15% (rollups, employer taxes, benefits load, GL journal view, headcount reconciliation)
4. AI/ML Integration — 15% (one feature done deeply: NL query over workforce data via Anthropic API, with HR-data guardrails)
5. UI/UX — 10% (CHRO-usable dashboard; functional clarity over polish)
6. Technical Execution — 5% (loads without errors, clean deploy)
7. Presentation & docs — 10% (README + architecture doc)

Depth beats breadth. A smaller feature set that works flawlessly beats a broad one that half-works.

## Tech stack

- Next.js 14+ (App Router, TypeScript) — single repo, API routes for server logic
- **Local dev: SQLite via Prisma ORM.** No Supabase/Vercel account exists yet, so the app runs entirely local-first (`prisma/dev.db`, zero external dependencies) until those accounts are created. See "Postgres migration path" below for the swap to Supabase for deployment.
- No auth/RLS (out of scope per the exercise; RBAC is mocked in the UI with a persona switcher)
- Recharts for charts, Tailwind for styling, shadcn/ui-style components (hand-rolled, no CLI init since it requires network access we may not have)
- Anthropic API (`claude-sonnet-4-5` or newer) for the NL query feature — tool-use pattern, never raw SQL from the model. Requires `ANTHROPIC_API_KEY` — feature degrades gracefully (clear message, not a crash) if the key is absent.
- Synthetic data generated by a seed script (`prisma/seed.ts`), deterministic with a fixed RNG seed so the demo is reproducible

### SQLite adaptations (deliberate, documented in README)

SQLite via Prisma does not support native enums or a first-class `Json` column type the way Postgres does. Adaptations:

- All `enum` fields below become `String` columns in the actual `schema.prisma`, with the allowed values enforced in a single TypeScript source of truth (`lib/enums.ts`) and validated at every write boundary with zod. The conceptual model — and the Workday mapping — is unchanged; this is a SQLite-connector limitation, not a design choice.
- `Json` fields are stored as `String` (JSON-serialized) in SQLite and parsed/validated with zod on read. On Postgres these become native `Json` columns — no schema change needed elsewhere.
- `Decimal` fields use Prisma's `Decimal` type (SQLite stores as a normalized string internally) and are handled with `decimal.js` in application code — never native floats for money.

### Postgres migration path (for real deployment)

When a Supabase project exists: change the `datasource` provider to `postgresql`, point `DATABASE_URL`/`DIRECT_URL` at Supabase, convert the `String` enum columns back to native Postgres `enum` types (mechanical find/replace, listed in `prisma/POSTGRES_MIGRATION.md`), convert the `Json`-as-`String` fields to native `Json`, and deploy to Vercel with the same env vars. No application logic changes — `lib/enums.ts` and the zod schemas stay as the validation layer regardless of DB engine.

## Core design principles

- **Everything effective-dated.** No mutation of worker attributes in place. State changes happen through `WorkerEvent` rows; current state is a derived view.
- **Master data vs. transactions strictly separated.** Dimensions (worker, position, org, location, job profile, comp grade) never carry transactional history; events do.
- **Positions are first-class.** A worker fills a position; a position belongs to a supervisory org and a job profile. Transfers move a worker between positions. Open positions = open reqs KPI.
- **The BP engine is generic.** `BpDefinition` → `BpStep` (with condition rules) → `BpInstance` → `BpStepInstance` (the audit trail). "Worker Data Change" is just one BP definition; the engine could run others. This mirrors Workday's BP framework and is explained in the README with a mapping table.
- **Multi-currency handled explicitly.** Salaries stored in local currency + currency code; an `FxRate` table converts to USD for all rollups. Fixed demo rates: GBP→USD 1.27, CAD→USD 0.73, INR→USD 0.012. Every USD figure in the UI is derived, never stored as the primary value.
- **Non-Active statuses are not an afterthought.** On Leave, Termination Pending, and Contractor workers exist in the seed data and drive the payroll reconciliation view.

## Data model (implement as written in `prisma/schema.prisma`, extend only additively)

Conceptual model (see actual `schema.prisma` for the SQLite-adapted field types):

```
// ---------- DIMENSIONS (master data) ----------

Worker { id, legalName, preferredName?, countryCode, hireDate, status(WorkerStatus), positions[], events[], compHistory[] }
WorkerStatus enum: ACTIVE ON_LEAVE TERMINATION_PENDING TERMINATED CONTRACTOR

SupervisoryOrg { id, name, parentId?, parent?, children[], managerId?, positions[] }

JobProfile { id, title, level, track(Track), positions[], compBands[] }
Track enum: IC M

Location { id, name, countryCode, positions[] }

Position { id, supOrgId, jobProfileId, locationId, status(PositionStatus), assignments[] }
PositionStatus enum: OPEN FILLED CLOSED

PositionAssignment (effective-dated worker<->position link) {
  id, workerId, positionId, effectiveFrom, effectiveTo?  // null = current
}

CompBand { id, jobProfileId, countryCode, currency, bandMin, bandMid, bandMax }

CompRecord (effective-dated compensation) {
  id, workerId, annualSalary(LOCAL currency), currency, effectiveFrom, effectiveTo?, reason
}

FxRate { currency, toUsd }  // USD implicit 1.0

// ---------- TRANSACTIONS (events) ----------

WorkerEvent {
  id, workerId, type(EventType), effectiveDate, payload(Json), bpInstanceId?, createdAt
}
EventType enum: HIRE TERMINATION TRANSFER COMP_CHANGE STATUS_CHANGE PROMOTION

// ---------- BUSINESS PROCESS ENGINE ----------

BpDefinition { id, name, steps[], instances[] }

BpStep {
  id, definitionId, order, name, assigneeRule, conditionRule?(JSON-logic string)
}
// assigneeRule: INITIATOR | MANAGER_OF_WORKER | SKIP_LEVEL_MANAGER | HR_PARTNER | COMP_PARTNER

BpInstance {
  id, definitionId, subjectWorkerId, initiatorId, status(BpStatus),
  proposedChange(Json), createdAt, completedAt?, stepInstances[]
}
BpStatus enum: IN_PROGRESS COMPLETED DENIED CANCELED

BpStepInstance (THE AUDIT TRAIL) {
  id, instanceId, stepName, assigneeId, action(StepAction), comment?, actedAt?, createdAt
}
StepAction enum: PENDING APPROVED DENIED SKIPPED_BY_RULE SENT_BACK

// ---------- WORKFORCE PLANNING ----------

Scenario {
  id, name, description?, assumptions(Json), createdAt
  // assumptions: { hirePlan: [...], attritionByDept: {...}, meritByLevel: {...}, meritEffectiveDate }
}
```

**Current-state derivation rule:** a worker's current department/location/level/salary is computed from the latest `PositionAssignment` + `CompRecord` where `effectiveTo IS NULL`. One server-side helper `getWorkforceSnapshot(asOfDate)` is used by every view — dashboard, planning baseline, payroll — so numbers always tie out.

## Seed data spec (`prisma/seed.ts`)

Deterministic (seeded RNG, seed = 42). ~350 workers.

- Department mix: GPU Cloud 30%, On-Prem 15%, Engineering 40%, G&A 15%.
- Locations: US majority (SF, SJ, Remote-US ≈ 75%), Canada (Toronto ≈ 8%), UK (London ≈ 8%), India (Bangalore ≈ 9%).
- Include verbatim the 12 sample employees from the exercise (E0001–E0010, E0148, E0149), including E0006 at 85,000 GBP, E0008 at 225,000 CAD, E0009 at 4,500,000 INR (the exercise writes it lakh-style as "45,00,000"), E0148 Termination Pending, E0149 On Leave.
- Non-active population: ~4% On Leave, ~1% Termination Pending, ~3% Contractor.
- Level distribution roughly pyramid: IC2–IC4 bulk, IC5/IC6 senior, M4–M6 management chain that produces a coherent org tree rooted at E0000 (CEO placeholder).
- Salaries drawn within comp bands per level/country; a deliberate ~10% of workers seeded below band-mid and a few above band-max (feeds the NL query demo and anomaly narratives).
- Hire dates spread 2019–2025 for a real tenure distribution; include ~25 hires in the trailing 12 months and ~30 terminations over trailing 12 months as TERMINATION events (feeds attrition KPI and headcount trend chart).
- Open positions: ~15 OPEN positions (feeds "open reqs" KPI).

Every distribution assumption above is echoed into `README.md` under "Data assumptions".

## Payroll preview rules (semi-monthly, one period)

- Gross per period = current annual salary / 24, in local currency; convert to USD via `FxRate` for rollups. Show both.
- Employer taxes (approximations from the exercise — implement as a per-country strategy function, documented):
  - US: 7.65% FICA (assume no one has hit the $168,600 SS wage base mid-year — stated assumption), + 6.2% SUI and 0.6% FUTA on first $7,000 (apply only to current-year hires — stated assumption).
  - UK: 13.8% employer NI above secondary threshold (£9,100/yr → £379.17 per semi-monthly period).
  - Canada: 7.5% blended CPP+EI.
  - India: employer PF = 12% × basic, basic = 50% of gross.
- Benefits load: 10% of gross (US), 5% (international).
- Who gets paid: ACTIVE + TERMINATION_PENDING (full period, flagged), CONTRACTOR excluded (flagged), ON_LEAVE configurable paid/unpaid toggle (default unpaid, flagged). Mid-period hires prorated by calendar days.
- **Reconciliation panel (required):** Active worker count vs. payroll headcount vs. total worker count, with an itemized delta table naming every excluded/flagged worker and the reason. This is a rubric line item — make it prominent.
- **Anomaly signal:** flag any worker whose current-period gross deviates >10% from their trailing 3-period average (simulate trailing periods from comp history), and any department whose burdened cost deviates >5% from the prior period. Each flag carries a plain-English explanation string.
- **GL posting view:** journal entry table — debit rows per department (cost center) × account (6000 Salaries & Wages, 6100 Employer Taxes, 6200 Benefits), single credit row 2100 Accrued Payroll. Must balance to the cent; show the balance check.

## Workforce planning rules

- Baseline = `getWorkforceSnapshot(today)`.
- Assumptions per scenario: hire plan (dept × quarter × count × level × location × start month), annualized attrition % per dept (applied monthly as rate/12 against dept headcount, deterministic expected-value math — no random draws), merit % per level with configurable effective date.
- Project 12 months forward: monthly headcount and fully-burdened monthly cost per dept (reuse the payroll burden functions so planning and payroll math agree).
- Scenario CRUD: create, name, clone, save. Ship two pre-built scenarios: "Plan of Record" and "IPO Readiness (slower G&A, faster Eng)".
- Comparison view: 2+ scenarios side by side — ending headcount, total 12-mo comp cost, delta in $ and %, plus a line chart of monthly headcount and monthly cost overlaying scenarios.

## AI feature: Natural-language workforce query (the one deep feature)

- Chat panel ("Ask People OS") calling the Anthropic API server-side (`/api/ask`).
- Pattern: tool use, not text-to-SQL. Define 4–6 typed tools the model can call: `query_workers(filters)`, `get_headcount_summary(groupBy)`, `get_comp_vs_band(filters)`, `get_attrition(period)`, `draft_document(type, workerId, context)`. Server executes against Prisma with validated params. The model never sees or writes SQL.
- Must handle the exercise's own example: "everyone in Engineering hired in the last 12 months whose comp is below band midpoint."
- Also support `draft_document` for a promotion announcement draft (second exercise example) — generated text is clearly labeled DRAFT and requires no side effects.
- **Guardrails (document in README):** server-side only, tool allow-list with zod-validated params, no PII beyond the synthetic dataset, responses grounded in tool results only (system prompt instructs the model to refuse to speculate), rate-limited endpoint, and a written note on responsible use for HR data (aggregate-first answers, no individual attrition-risk inference surfaced without governance).

## UI structure

- `/` Dashboard: KPI cards (total headcount, monthly run-rate burdened cost USD, trailing-12-mo attrition %, open reqs, % international) + headcount trend chart (13 months) + dept×level stacked bar.
- `/workers` Directory: filterable table, row → worker detail with effective-dated history timeline (comp, position, events) — this page is the effective-dating demo.
- `/processes` BP inbox: persona switcher (act as Manager / Skip-level / HR Partner), pending approvals, approve/deny/send-back with comment, full audit trail per instance, and a "start worker data change" flow (comp change or transfer). Conditional routing demo: comp change >10% inserts a Comp Partner approval step; ≤10% skips it (rendered as SKIPPED_BY_RULE in the trail so the routing is visible).
- `/planning` Scenarios: assumption editor, projection charts, scenario list.
- `/planning/compare` Comparison view.
- `/payroll` Payroll preview: period selector, dept/location rollups, worker-level drill-in, reconciliation panel, anomaly flags, GL posting tab.
- `/ask` NL query chat.

Layout: left sidebar nav, top bar with persona switcher. Clean, data-dense, no gimmicks.

## Engineering rules for this repo

- TypeScript strict. All money in `Decimal`/`decimal.js` server-side; format at the edge. Never float-math currency.
- One shared module `lib/payroll.ts` for all burden math; `lib/snapshot.ts` for point-in-time derivation; `lib/bp-engine.ts` for the process engine. UI never re-implements business math.
- Seed script must be idempotent (`prisma migrate reset && seed` is the reset path).
- Every page renders with zero console errors and no loading spinners longer than ~2s on seeded data (precompute/paginate where needed).
- Env vars: `DATABASE_URL` (SQLite file locally), `ANTHROPIC_API_KEY` (optional locally — feature no-ops gracefully without it). Never expose the Anthropic key client-side.
- Commit at the end of every phase with a descriptive message. Keep commits reviewable.
